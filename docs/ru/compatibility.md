# Совместимость

Руководства описывают пакет **0.1.0-preview.5** с одной сборкой для `net10.0`. API предварительный и может меняться. Доступность пакета в публичном NuGet и обязательство сохранять стабильный API не установлены. В [начале работы](getting-started.md) используется локально собранный пакет.

<a id="reference-api"></a>
## Опорное сочетание версий

| Компонент | Опорное значение |
|---|---|
| Целевая платформа | `net10.0` |
| Запрос SDK в репозитории | `10.0.100`, `latestFeature`, предварительные SDK отключены |
| Опорный разрешённый SDK | `10.0.401` |
| EF Core Relational | `10.0.12` |
| EF-провайдер Npgsql | `10.0.3` |
| Npgsql | `10.0.3` |
| Плагин Npgsql NodaTime для проверки совместной работы | `10.0.3` |
| PostgreSQL | `16.14` |
| Целевая версия генерации SQL Npgsql | `14.0` |

Fixture PostgreSQL использует `postgres:16-alpine@sha256:33f923b05f64ca54ac4401c01126a6b92afe839a0aa0a52bc5aeb5cc958e5f20`. Digest обеспечивает воспроизводимый вход тестов. Отдельная проверка изоляции контекстов с SQL target `15.0` не устанавливает поддержку серверов PostgreSQL 14/15.

Запрос SDK допускает переход между feature band; потребителям не требуется закреплять SDK `10.0.401`. Библиотека не меняет политику SDK приложения.

<a id="dependency-api"></a>
## Диапазоны зависимостей и поддержка

Метаданные пакета задают EF Core Relational `[10.0.12,11.0.0)` и Npgsql/provider `[10.0.3,11.0.0)`. Интервалы разрешают NuGet выбирать версии внутри major 10, но не подтверждают каждую допустимую patch-версию. В таблице приведено опорное сочетание для провайдерных и пакетных проверок; другое сочетание оценивается по собственным результатам проверки.

Генератор SQL для блокировок использует внутренние API провайдера, чувствительные к версиям. Обновление EF/Npgsql требует соответствующих проверок компиляции, реального провайдера и изолированного потребителя пакета. Дополнительные TFM, EF Core 8/9/11, другие patch/major PostgreSQL, NativeAOT и trimming находятся за пределами описанной проверенной поддержки. Для расширения нужны явное решение и проверки новых границ.

<a id="feature-api"></a>
## Границы возможностей

| Семейство | Текущая поддержка |
|---|---|
| [Блокировки](query-integration.md) | Закрытый набор запросов к корневой сущности и advisory-ключи на время транзакции; общие JOIN/проекции и упорядоченный многострочный протокол по набору ключей исключены |
| [Данные и транзакции](internal-mechanisms.md) | Вставка одной строки с пропуском выбранного конфликта, mapping/чтение времени и команда только для чтения с описанными ограничениями моделей и транзакций |
| [Настройка и диагностика](capabilities.md) | Явная проверка требований к базе только для чтения; готовностью и выбором SQL target управляет приложение |

Поддерживается регистрация обычных контекстов, фабрик и пулов с провайдером Npgsql; ручная композиция внутреннего service provider и конкурирующие замены генератора SQL/транслятора исключены. Дополняющее поведение NodaTime проверяется отдельно. Автоматических транзакций, повторов и правил восстановления приложения нет.

<a id="release-api"></a>
## Проверки и выпуск

Linux workflow собирает библиотеку, выполняет полный набор провайдерных тестов, создаёт пакет и запускает его изолированного потребителя на PostgreSQL. Windows workflow собирает библиотеку и выполняет unit-тесты. Для полного провайдерного запуска и проверки потребителя нужен Docker или совместимая среда контейнеров. Команды приведены в [Contributing](https://github.com/Keeyahto/EntityFrameworkCore.PostgreSQL.Extensions/blob/develop/CONTRIBUTING.md).

Заявленная поддержка требует соответствующих фактических результатов. Сборка, выполнение на провайдере, создание локального пакета, изолированное потребление и публикация устанавливают разные факты. Старые отчёты о запусках и количества тестов сохраняются в истории Git; действующие руководства содержат контракты и инструкции. Наличие workflow или этой страницы не доказывает успешный текущий запуск или опубликованный релиз.

Артефакт, который выпущен или выбран потребителем по точной версии/хешу, сохраняется неизменным. Изменённый артефакт выпускается под новой версией. Документацию можно коммитить независимо; повторная упаковка встроенного README для распространения создаёт другой артефакт пакета. Описание изменений помещается в changelog, а публикация требует разрешения сопровождающего и реальных прав учётной записи.
