# Блокировки

Блокировка строк защищает существующие строки, пока ваша транзакция читает и изменяет их. Advisory-блокировка на время транзакции согласует работу участников по ключу, в том числе до появления строки. Обе формы требуют текущую явную транзакцию EF и освобождаются PostgreSQL при её завершении.

Примеры используют модель из [начала работы](getting-started.md). Для блокировок строк нужна [регистрация](capabilities.md#registration-api); advisory-блокировкам достаточно провайдера Npgsql.

<a id="row-locks-api"></a>
## Блокировки строк

```csharp
await using var transaction = await db.Database.BeginTransactionAsync(ct);
var document = await db.Documents
    .Where(x => x.Id == 1)
    .ForUpdate(LockWait.NoWait)
    .SingleAsync(ct);
document.Payload = "changed";
await db.SaveChangesAsync(ct);
await transaction.CommitAsync(ct);
```

Запрос добавляет `FOR UPDATE OF` для сгенерированного псевдонима корневой таблицы. Если другая транзакция держит несовместимую блокировку, `NoWait` приводит к ошибке PostgreSQL «блокировка недоступна». Запрос с маркером либо получает требуемую блокировку точного проверенного вхождения таблицы, либо завершается явной ошибкой. Успешный возврат якобы заблокированных данных после молчаливой потери маркера недопустим.

<a id="modes-api"></a>
### Сила блокировки и ожидание

| API или значение | Поведение PostgreSQL |
|---|---|
| `ForUpdate()` / `ForUpdate(wait)` | `FOR UPDATE`; наиболее сильная блокировка строк |
| `ForShare()` / `ForShare(wait)` | `FOR SHARE`; допускает совместимые разделяемые блокировки чтения |
| `WithRowLock(LockStrength.NoKeyUpdate, wait)` | `FOR NO KEY UPDATE` |
| `WithRowLock(LockStrength.KeyShare, wait)` | `FOR KEY SHARE` |
| `LockWait.Wait` | Ждать несовместимую блокировку; значение по умолчанию в вызовах без аргументов |
| `LockWait.NoWait` | Сразу завершиться ошибкой при несовместимой блокировке |
| `LockWait.SkipLocked` | Пропустить строки, которые нельзя заблокировать немедленно |

`WithRowLock` также принимает `LockStrength.Update` и `LockStrength.Share`. Оба аргумента, сила и ожидание, обязательны. Их значения должны быть структурными константами, в том числе в скомпилированных запросах. Параметры времени выполнения, выбирающие ключевые слова блокировки в скомпилированном запросе, отклоняются. Повторные маркеры отклоняются даже при совпадении режимов.

`SkipLocked` подходит только там, где допустим пропуск занятых строк. Полнота результата и справедливость распределения работы не гарантируются. Выбирайте силу с учётом [совместимости блокировок PostgreSQL](https://www.postgresql.org/docs/16/explicit-locking.html#LOCKING-ROWS).

<a id="query-shapes-api"></a>
### Поддерживаемые запросы и модели

Набор разрешённых форм закрыт. Для полного запроса должны выполняться все условия:

| Часть | Допустимая форма |
|---|---|
| Корень | Одна обычная сущность, напрямую отображённая на одно однозначное вхождение таблицы; материализуется сама сущность |
| Отслеживание | Запросы с отслеживанием и `AsNoTracking` |
| Предикат | Равенство прямых отображённых скалярных свойств константам или извлечённым параметрам EF; несколько равенств через `AND` |
| Ключ | Первичный, естественный или составной при тех же правилах; nullable-свойства и преобразователи сохраняют ограничения явно проверенных отображений |
| Место маркера | До или после допустимого `Where` |
| Завершение | `Single`, `SingleOrDefault`, `First`, `FirstOrDefault`, их асинхронные варианты либо синхронное/асинхронное перечисление сущностей |
| Упорядоченный выбор одной строки | `OrderBy`/`OrderByDescending` по прямому скалярному столбцу, необязательный `ThenBy`/`ThenByDescending`, затем один `Take(1)`; без смещения |
| Повторное использование | `EF.CompileQuery` и `EF.CompileAsyncQuery` с постоянными режимами блокировки; обычный кэш запросов |
| Теги | Обычные постоянные пользовательские теги; внутренний протокол и динамические теги блокируемого запроса отклоняются |

C# повышает операнды равенства `short` до `int`. Валидатор допускает встроенное преобразование `short` в `int` без метода и lifted-семантики вокруг одного прямого отображённого свойства, а при наличии — такое же преобразование короткой константы/параметра. Пара преобразований проверяется и сохраняется в выражении. Остальные приведения, вычисляемые свойства и пользовательские преобразования отклоняются. Целочисленный параметр за пределами диапазона столбца `smallint` по-прежнему может вызвать штатное переполнение провайдера; библиотека не сужает значения.

До отправки запрошенного SELECT отклоняются:

- JOIN, LEFT JOIN, self-join и несколько целей; проекции, включая тождественный `Select`;
- `Include`, split queries, автоматически загружаемые навигации и глобальные фильтры, в том числе именованные;
- навигации и цепочки свойств, подзапросы в предикатах, методы, `OR`, неравенства и вычисление на клиенте;
- корни из raw SQL/функций, представления, наследование, owned/complex, совместное или раздельное отображение таблиц;
- вложенные блокировки и перенос в подзапрос, `Skip`, произвольный или повторный `Take`, `Distinct`, группировки, агрегаты, `Any`/`Count` и операции над множествами;
- повторные маркеры, динамические режимы и прочие неизвестные формы.

Знакомое имя оператора не разрешает любую его перегрузку или выражение. Нестандартные отображения за пределами проверенных случаев требуют собственной проверки на PostgreSQL. Упорядоченные многострочные блокировки по массиву/набору ключей в текущую поддержку не входят.

<a id="selection-api"></a>
### Выбор строки и конкуренция

Пример упорядоченного выбора одной строки:

```csharp
await using var transaction = await db.Database.BeginTransactionAsync(ct);
var documents = await db.Documents
    .OrderBy(x => x.Id)
    .Take(1)
    .ForUpdate(LockWait.SkipLocked)
    .ToListAsync(ct);
await transaction.CommitAsync(ct);
```

Результат может быть пустым. На READ COMMITTED оператор `ORDER BY` не задаёт универсальный порядок захвата блокировок и не гарантирует, что после ожидания и конкурентного изменения ключей вернувшаяся строка останется первой по сортировке. `Single` сохраняет штатную проверку количества результатов и может заблокировать просмотренные строки до обнаружения нескольких совпадений. Выбор уникального предиката, длительности и порядка работы остаётся за приложением.

<a id="transaction-api"></a>
### Транзакция, кэш и ошибки

Построить запрос и вызвать `ToQueryString()` можно до начала транзакции. При выполнении нужна текущая явная транзакция EF на том же соединении, что и команда. Подходит корректно присоединённая через EF `UseTransaction` чужая транзакция; одного ambient `TransactionScope` недостаточно. Библиотека не начинает, не фиксирует, не откатывает и не повторяет транзакции за вас.

Проверки охватывают исходное выражение/модель, окончательную структуру запроса и выполнение команды. Проверяются установленные сервисы, исполнение запроса на блокировку и фактический параметр `Take(1)`, включая кэшированные и скомпилированные запросы. Повторное использование кэша не разрешает последующий `Take(2)`. Внутренние теги — деталь реализации без разрешительных свойств; поддельный текст протокола отклоняется и в обычных пользовательских тегах.

Отмена передаётся дальше. Ошибки PostgreSQL, включая конфликт блокировки (`55P03`), сбой сериализации (`40001`), deadlock (`40P01`) и завершение backend (`57P01`), остаются распознаваемыми через штатные обёртки EF/Npgsql. Обработкой ошибки и состоянием транзакции управляет приложение. См. [диагностику](capabilities.md#troubleshooting-api).

<a id="advisory-api"></a>
## Координация через advisory-блокировки

Advisory-блокировка представляет ключ, выбранный приложением. В протоколе участвуют только операции, которые получают ту же advisory-блокировку; произвольный SQL автоматически под её защиту не попадает.

```csharp
await using var transaction = await db.Database.BeginTransactionAsync(ct);
await db.Database.AcquireTransactionAdvisoryLockAsync("document:1", ct);
var inserted = await db.InsertIgnoreAsync(
    new Document { Id = 1, Payload = "created" }, x => x.Id, ct);
await transaction.CommitAsync(ct);
```

Договоритесь об общей схеме ключей для всех участников. Так можно согласовать работу ещё до появления соответствующей строки. Поддерживаемые перегрузки возвращают `Task`:

```csharp
await db.Database.AcquireTransactionAdvisoryLockAsync("document:1", ct);
await db.Database.AcquireTransactionAdvisoryLockAsync(123L, ct);
await db.Database.AcquireTransactionAdvisoryLockAsync(7, 123, ct);
```

Каждая строка выше — самостоятельный пример перегрузки для выполнения внутри транзакции приложения. Текстовый ключ обрабатывается PostgreSQL через `pg_advisory_xact_lock(hashtextextended(key, 0))`. Хеширование допускает коллизии и использует то же пространство bigint, что и перегрузка `long`. Пространство двух int в PostgreSQL отделено от пространства bigint. Не считайте похожие по записи текстовые, bigint и двухкомпонентные ключи одной блокировкой.

Операции блокирующие и ограничены временем транзакции. Ожидание можно отменить; PostgreSQL освобождает блокировку при завершении транзакции. Сессионного запасного режима, try-lock API, автоматических повторов и обработки коллизий нет.
